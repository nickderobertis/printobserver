# printobserver-oneharness

The constraints this crate is held to, and why each one is worth its cost.
What the code currently *does* is in the manifests, the graph targets and the
suite; nothing here restates them. `repo-policy.toml`'s `[supervisor]` section
is the machine-readable half of the first three, and `just check-repo` enforces
them from there rather than from this file.

## Nothing in this crate spawns

No source of it may use a process-spawning interface at all — not
`std::process::Command`, not an alias of it, not a name computed at run time.
The check refuses the *interfaces* rather than the executables, because a rule
keyed on the word `oneharness` is one a computed name walks straight past.

Processes still exist during a turn: OneHarness spawns the harness itself. That
is why the port carries a seam a caller watches a turn through rather than a
promise that nothing runs — a watchdog reaps the harness tree, and this
repository's own suite reads every process created under a run off the same
seam.

## What a prompt may say is one committed file

The template is the whole of it: three slots filled and sent unchanged, and a
system prompt read from the tree rather than carried in this crate's text. A
rule about what the agent may be told is then a rule about one file a person
reads, instead of a claim about code spread over a turn.

The template may name no operation of this program but the context read, and
that forbidden set is *derived* from the generated `PrintAction` vocabulary
rather than restated, so a variant the contracts gain is covered the moment the
generation target writes it. The rule is keyed on those names rather than on
words that sound like instructions: an event saying the printer paused is a
fact, and a rule hunting such words would refuse a truthful description while
missing an instruction phrased another way.

## The answer is constrained by the generated schema

What reaches OneHarness is the *path* of the contracts' own checked-in
artifact, which it reads per run, and this crate may carry no schema file of its
own. A copy of the generated bytes passes a content comparison while defeating
the thing that comparison is for, so the claim is about identity and drift
rather than about content: the artifact this crate points at is the one the
generation target writes, and changing that artifact changes what the port
accepts.

## Nothing about a live session is held in memory

One session per print, named from that print's own identifier, is a file under
the configured state directory, and OneHarness's own session store lives beside
it. That is what lets the supervisor be restarted between two events of one
print and have the second continue the first's conversation — the property the
whole port exists for, since a supervisor with amnesia pauses a print it
already decided was fine.

A print whose session has been closed — by a terminal state, by abandonment, or
by the harness refusing to continue a session it did not create — opens the next
of the sequence rather than resuming the closed one. None of that reaches the
caller as a failure: closing and reopening is ordinary supervision, and a caller
that had to handle it would be handling OneHarness's session model.

## What cannot be valid is not representable

A configuration reaches this port already narrowed — an empty harness identity
selects nothing, a zero turn timeout expires every turn before it starts, and a
bare string need not be an assignment at all — so no step downstream re-checks
what an earlier one could have let through.

The persisted ledger is held to the same standard from the other side. Its
format is a closed set rather than free text, and a record is refused unless it
is the shape this build writes and is the ledger of the print it was selected
by. Both are refusals rather than repairs: a shape this build does not know is
one whose fields it would be guessing at, and a ledger holding another print's
sessions under this print's name is a state directory rearranged underneath the
supervisor. Reading either as this print's own history is how one print's
conversation ends up continuing another's.

A finished run is narrowed once, in one place, to the result and the session a
turn is written down from. A run carrying neither is refused rather than
recorded: nothing ran that could be attributed to a conversation, and a ledger
carrying turns of a session that was never opened reads as though the agent had
been consulted.

## Testing it costs no model call

The one thing a journey here may replace is the paid provider process, and it
is replaced by the deterministic responder OneHarness publishes for the purpose
— which keeps that engine's own argument construction, parsing, session store
and schema validation. Everything from the run request down is therefore the
real OneHarness, and nothing doubles the port: a double would prove this
repository's idea of the engine rather than the engine.

What that costs is a binary of this repository's own for the engine to resolve
to, and it is kept off what a consumer installs — a test seam that ships is a
paid provider somebody can replace in production.

That suite also **writes** to the checked-in schema tree, which is the one place
it acts on something outside its own scratch directory. Proving the answer is
constrained by the *generated* artifact rather than by a copy of its bytes means
changing that artifact on disk and watching an answer that was accepted be
refused; a scratch copy the port was pointed at would not be the artifact the
claim is about. Every suite that reads that tree runs at the same time, so all of
them serialize on one operating-system lock named by `repo-policy.toml` —
`just check-repo` holds every declared holder to that one name, because two
suites locking two different files are back to no lock at all.
